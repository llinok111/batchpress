### How upstream is used

batchpress calls only the public API:

- `sharp(input, { failOn: 'truncated', limitInputPixels })`
- `.rotate()` — EXIF orientation
- `.resize()` — for the square-crop presets
- `.toFormat(format, options)` / `.toBuffer()`
- `sharp.concurrency(1)`, `sharp.cache(false)` — so the queue owns concurrency
- `.metadata()` — header-only probing, used by the planner

No upstream source file is modified, vendored, copied or patched. No upstream test is reused. The dependency is installed from the npm registry by the user; this package ships without `node_modules`.

## Why this is not a fork

The upstream is a library whose public contract is "one image in, one image out"; it has no queue, journal, retry, cancel or disk policy to extend (verified by `grep -ril` over `src/lib` for those terms — zero matches). Adding an opinionated batch state machine inside it would change its public surface and couple it to a fast-moving native dependency. Keeping the layer outside means the upstream can be upgraded by changing one version range, and the boundary is the single `toBuffer()` call.

## Not derived from

No code, test, fixture or documentation text from any other project was copied into batchpress. The image corpus is generated by `test/fixtures.mjs` from a seeded PRNG and is not taken from any dataset.
